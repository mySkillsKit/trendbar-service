# Trend bar service

## Терминология

### Symbol

[Ссылка на класс](./src/main/java/com/spotware/trendbar/model/Symbol.java)

Валютная пара (например, EURUSD, EURJPY).

### Quote

[Ссылка на класс](src/main/java/com/spotware/trendbar/model/Quote.java)

Обновление цены для конкретного символа в определённый момент времени.
Содержит новую цену, символ и временную метку.

### Trend bar (TB)

[Ссылка на класс](src/main/java/com/spotware/trendbar/model/TrendBar.java)

Также известен как свеча (candlestick) — агрегированные данные котировок для конкретного символа за заданный период trend bar'а.
Подробнее о trend bars (свечах) можно прочитать [здесь](https://help.ctrader.com/knowledge-base/chart-types/).

Обратите внимание, что бар не содержит всю информацию о котировках, на которых он построен.
Он содержит только следующие параметры:

* *open price* — цена символа в начале периода trend bar'а
* *close price* — цена последней полученной котировки в этом периоде
* *high price* — максимальная цена за период
* *low price* — минимальная цена за период
* *trendbar period* — определённый временной интервал, в течение которого аккумулируются котировки (например, M1 — одна минута, H1 — один час, D1 — один день и т.д.)
* *timestamp* — момент времени, в который начинается период trend bar'а

Trend bar всегда начинается в начале своего временного периода.
Для минутных trend bar'ов это 00:00:00, 00:01:00 и т.д.
Для часовых — 00:00:00, 01:00:00 и т.д.

Время котировки и серверное время могут отличаться, но TB строится на основе временных меток котировок.

### Completed TB

TB, временной интервал которого уже закончился. Например, для M1 completed-баром считается тот, чьё начало приходится на минуту, предшествующую текущей.

![img.png](Trendbars.png)

### TB history

Набор completed TBs, чьи timestamp'ы начала попадают в заданный период.

## Описание задачи

Предположим, что есть три типа trend bars: M1 (минутный), H1 (часовой) и D1 (дневной).
Необходимо реализовать trend bar service, который:

1. Строит TBs на основе получаемых котировок. То есть сервис должен поддерживать набор текущих TBs, обновлять их при каждой котировке и сохранять в storage, как только период trend bar'а закончен.
2. Предоставляет историю trend bar'ов по запросу. А именно: возвращает набор TBs по имени символа, периоду, а также временной метке *from* и временной метке *to*. Если *to* не указан, метод должен вернуть все TBs между *from* и текущим временем.

Для проверки работоспособности решения необходимо реализовать интеграционный тест, симулирующий high-load сценарий.

## Общие требования

1. Исходный код должен компилироваться. Если нет — задача не считается выполненной.
2. Код должен быть покрыт тестами. Можно использовать JUnit или TestNG.
3. Важно сделать код максимально чистым (в смысле книги *Clean Code* Дядюшки Боба) и понятным. Не тратьте время на Javadoc — хороший код документирует себя сам.
4. Код должен быть отформатирован согласно стандартному [Java Code Style](https://www.oracle.com/java/technologies/javase/codeconventions-contents.html).
5. TB-сервис должен обрабатывать получаемые котировки асинхронно — то есть не в потоке, который их передаёт, а помещать во внутреннюю структуру для дальнейшей обработки другим потоком. Желательно иметь тривиальные реализации quote-провайдера для интеграционных тестов.

## Ограничения и пояснения

1. **Keep it simple.**
2. **Не использовать Spring framework ни для чего кроме dependency injection.**
   DI — очень полезный подход, не стесняйтесь его применять, где это уместно. Иначе мы увидим не ваш код, а «Spring magic».
3. **Использовать Test Driven Development при реализации задачи.**
   Это поможет писать чистый и компактный код.
4. **Использовать предоставленные классы и интерфейсы.**
   Они нужны, чтобы сэкономить время — ваше и наше. При необходимости их можно расширять.

История TB включает только completed TBs.

Storage TB может быть in-memory (не in-memory СУБД, а просто структура данных в Java heap).
Помните, что котировки приходят в одном потоке, а запросы истории могут поступать из другого.

Котировки приходят в естественном порядке — timestamp каждой следующей всегда больше предыдущей.

Количество получаемых котировок в минуту может быть очень большим.

Trend bar должен обновляться как можно быстрее при получении котировки.

Временные зоны в этой задаче не важны. Допустимо использовать Unix time в миллисекундах.

Имейте в виду, что trend bar service — это модуль системы, а не самостоятельное приложение, поэтому не нужно выставлять сервис через web service или реализовывать UI.
